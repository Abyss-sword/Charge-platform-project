## 3. 第一优先级：统一模拟器计量语义

### 3.1 必须确认的字段含义

`PILE_TELEMETRY.energyKwh`推荐定义为“电桩生命周期累计电量读数”，而不是当前订单用电量。

成员3需要保证：

- 同一电桩的累计读数正常情况下只能增加或保持不变；
- 重复上报同一读数不会额外增加订单费用；
- 设备重启后不能随意从零开始；
- 时间戳必须包含时区；
- 上报时间不能倒退；
- `pileId`必须对应成员1数据库中的`pile_info.id`；
- 模拟器显示“发送成功”前必须确认服务端返回成功。

### 3.2 与成员1共同冻结的规则

累计读数转换为订单电量的推荐公式：

```text
当前订单电量 = 当前累计读数 - 订单开始时累计读数
```

例如：

```text
订单开始前累计读数：100.00 kWh
订单充电后累计读数：108.35 kWh
本次订单实际电量：  8.35 kWh
```

成员3负责提供可靠累计读数；成员1负责保存订单起始读数、计算差值和写入订单。以下边界必须在联调前共同确定：

- 订单开始时还没有设备读数怎么办；
- 设备更换或计量表归零怎么办；
- 迟到数据和重复数据如何处理；
- 订单停止后的遥测是否还能改变已结算金额；
- 下一笔订单如何建立新的起始值；
- `ORDER_TELEMETRY`旧入口是否保留，以及谁可以调用。

在这些规则冻结前，成员3不要自行把电桩累计值直接写成订单电量，也不要让FastAPI修改订单表。

## 4. 第二优先级：建立可控模拟场景

模拟器至少应支持以下场景，并能通过命令参数、配置文件或界面按钮切换：

| 场景 | 输入行为 | 预期服务端结果 |
| --- | --- | --- |
| 正常在线 | 按固定间隔上报合法数据 | 心跳刷新，桩保持正常状态 |
| 正常充电 | 功率和累计电量稳定增加 | 遥测入库，联调完成后订单电量增加 |
| 高温告警 | 温度达到或超过70℃ | 桩进入故障，产生或复用过热告警和工单 |
| 离线 | 停止上报超过15秒 | 桩进入离线，产生或复用离线告警和工单 |
| 恢复 | 故障解除后恢复正常上报 | 桩按活动订单恢复相应状态 |
| 重复上报 | 重发同时间、同读数数据 | 不产生重复计费或重复活动告警 |
| 时间倒退 | 上报时间早于上一条记录 | 服务端明确拒绝 |
| 电量倒退 | 累计电量小于上一条记录 | 服务端明确拒绝 |
| 未知电桩 | 使用数据库不存在的`pileId` | 服务端明确拒绝，不写脏数据 |

推荐为每个场景提供稳定名称，例如：

```text
normal
charging
overheat
offline
recover
duplicate
time-backward
energy-backward
unknown-pile
```

答辩时应通过一个统一入口切换场景，不应临时修改源代码。

## 5. 第三优先级：FastAPI统一读取成员1数据库

### 5.1 数据库规则

- 数据库路径通过`CHARGE_PLATFORM_DB`或团队约定的统一配置传入；
- FastAPI只能使用只读连接；
- 不建立另一套独立业务数据库；
- 不直接修改订单、钱包、电桩、告警和工单；
- 支持成员1最新数据库迁移，包括006单价锁定字段；
- 查询失败时返回明确错误，不返回伪造成功数据；
- SQLite短暂忙碌时应合理返回或重试读操作，不能阻塞C++服务端写入。

### 5.2 至少提供的数据接口

| Web展示 | FastAPI应提供的数据 |
| --- | --- |
| 总览卡片 | 站点数、电桩数、在线率、充电中订单、今日服务量、今日营收 |
| 电桩状态 | 空闲、预约、充电、故障、离线数量 |
| 营收趋势 | 按小时或按天聚合的已完成订单营收 |
| 用电趋势 | 基于订单电量或遥测增量的趋势 |
| 告警列表 | 告警类型、级别、设备、状态和发生时间 |
| 工单列表 | 关联告警、负责人、处理状态和更新时间 |
| 数据质量 | 数据来源、更新时间、有效记录、异常记录和缺失情况 |

所有金额和电量应以十进制类型处理，输出固定两位字符串。不得使用普通二进制浮点数累计金额。

## 6. 第四优先级：修正大屏指标口径

### 6.1 用电量

如果`pile_telemetry.energy_kwh`是累计读数，同一时间段用电量不能直接执行：

```text
SUM(每条累计读数)
```

推荐算法：对每个电桩按时间排序，计算有效相邻读数差，再按时间段汇总。

```text
单次增量 = max(当前累计值 - 上一累计值, 0)
小时用电量 = 本小时各电桩有效增量之和
```

设备归零、倒退或跨越过长时间的数据应标记异常，不能直接参与汇总。

### 6.2 营收

- 仅统计`FINISHED`订单；
- 充值不属于充电营收；
- 使用十进制类型累计`amount_yuan`；
- 明确统计时区；
- 空数据返回`0.00`，不能返回空字符串或模拟数字。

### 6.3 利用率和在线率

建议分别计算：

```text
在线率 = 非OFFLINE电桩数 ÷ 电桩总数
即时使用率 = CHARGING电桩数 ÷ 可服务电桩数
可服务电桩 = IDLE + RESERVED + CHARGING
```

FAULT和OFFLINE不能计入正常可服务电桩。若项目采用其他定义，必须在页面和文档中明确分母。

### 6.4 预测

- 预测值不能直接复制实际值；
- 尚未训练模型时，应明确标注“规则估算”或“演示预测”；
- 至少划分训练区间和展示区间；
- 输出模型名称、更新时间、样本数及误差；
- 数据不足时显示“数据不足”，不能伪造高准确率。

第一阶段可使用移动平均、指数平滑或同时间段历史均值；第二阶段再切换线性回归、随机森林等模型。

| 方法 | 优点 | 局限 |
| --- | --- | --- |
| 移动平均 | 简单、稳定、容易解释 | 无法表达复杂趋势 |
| 指数平滑 | 更重视近期数据 | 参数需要选择 |
| 线性回归 | 可解释、实现容易 | 难以描述非线性关系 |
| 随机森林 | 能处理非线性与多特征 | 数据少时容易失真，解释较复杂 |

### 6.5 数据质量

数据库查询成功只代表“能够读取”，不代表“数据质量合格”。至少检查：

- 必填字段缺失；
- 时间格式和时区；
- 金额、电量两位小数格式；
- 电量或时间倒退；
- 不存在的站点、电桩或订单关联；
- 重复记录；
- 数据来源是否为`SIMULATED`。

## 7. 第五优先级：Web大屏实时刷新

Web大屏保持已确认的浅色商业化风格，建议每2～3秒通过HTTP请求FastAPI刷新数据。

刷新时要求：

- 不整页重新加载；
- 图表和卡片平滑更新；
- 保留最后一次成功数据，并显示“数据可能已过期”；
- 接口恢复后自动刷新；
- 页面明确显示最后更新时间和数据来源；
- 空数据、错误和加载中状态均有明确界面；
- 不因动画影响数字准确性和可读性。

三端联动时至少能看到：

1. Qt预约后预约/可用桩数量变化；
2. 开始充电后充电中订单数量变化；
3. 模拟器上报后遥测和电量趋势变化；
4. 支付后订单状态和营收变化；
5. 高温或离线后电桩、告警和工单变化；
6. 运营端处理工单后大屏状态变化。

## 11. 三端联调时成员3操作顺序

### 正常业务流程

1. 确认FastAPI和Web显示统一数据库及更新时间；
2. 成员2车主端登录、选站、选桩并预约；
3. 成员3模拟器对相同`pileId`开始正常上报；
4. 车主端开始充电；
5. 确认数据库遥测、订单电量及大屏趋势变化；
6. 车主端停止并支付；
7. 确认订单完成、余额减少、营收增加、电桩释放；
8. 刷新运营端和Web，核对三处数据一致。

### 故障运维流程

1. 对正在联调的电桩切换到高温场景；
2. 确认服务端产生过热告警和工单；
3. Web显示故障电桩、告警和工单；
4. 成员2运营端确认告警并处理工单；
5. 成员3模拟器恢复正常数据；
6. 运营端解决、关闭工单；
7. Web刷新后显示最终状态；
8. 核查没有重复活动告警或重复工单。
