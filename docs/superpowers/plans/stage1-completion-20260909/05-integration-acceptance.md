# 三端集成、第一阶段验收与交付操作指南

**Goal:** 在隔离候选版本上，验证车主、运营、设备和Web围绕同一数据库完整运行；保护原演示版本，提供可复现的通过或未通过结论。

**Architecture:** 成员1统一构建、协议和数据；成员2负责Qt双端；成员3负责设备和只读分析/大屏。一个总控管理根文件、候选版本及验收证据。

每个任务按“失败测试→最小实现→针对测试→必要回归→本地提交→交接”执行。报告至少包含实际改动、命令/退出码、剩余依赖；不能只说“代码已经完成”。可由一个Agent依顺序扮演三角色，不要求凑足三个Agent。

## 4. 测试环境准备

- 使用候选专属runtime和临时测试目录；数据库与头像根成对隔离。禁止将原运行库复制到仓库跟踪目录。
- 迁移按程序的实际迁移器顺序执行；seed只在空候选库初始化一次。不能既自动迁移又无条件重复手工SQL。种子数量以当前seed为准，历史3站/12桩/20用户/30订单等仅作核对线索，不硬改数据来满足旧数字。
- 运行 `PRAGMA integrity_check` 必须ok、`PRAGMA foreign_key_check`无行。重置先停止本候选相关进程，并采用现有已审查的备份脚本；路径不属于候选专用目录即拒绝。
- 教学账号、管理员/设备凭据放非跟踪配置；不上传真实个人信息。脚本记录身份编号而非令牌。
- 所有进程从同一候选工作树启动。API数据库与服务端一致；Web的代理目标对应本候选API，不指向旧服务。不要盲目采用Vite旧配置中的端口。
- 单测用临时数据库和系统分配端口；人工演示选确认空闲的候选端口。统一启动器应记录实际地址，但不打印秘密。

## 5. 构建及自动检查

在候选根执行（目标名和解释器以R0发现并在runbook冻结）：

```bash
cmake -S . -B build-stage1 -G Ninja -DBUILD_TESTING=ON
cmake --build build-stage1 -j2
ctest --test-dir build-stage1 -N
ctest --test-dir build-stage1 --output-on-failure --no-tests=error
git diff --check
git status --short
```

成员1负责根目标包含服务端、Qt车主/运营端和模拟器及必要测试。分析服务执行 `python -m pytest -q`（analytics工作目录，项目虚拟环境）；dashboard执行 `npm run test:run`、`npm run build`。依赖缺失先确认锁文件和隔离环境，必要安装需遵守工具授权，不强改全局版本。

新增建议 `tests/e2e/stage1_stack_test.py`：创建临时库→启动真实服务端及API→使用真实模拟器/PILE协议→用户协议操作→检查API与数据库→清理自己启动的进程。不得直接调用OrderService注入电量；不得替换API为mock再宣称整组通过。UI自动测试可以保留Mock夹具，但报告必须区分。

已有测试不因为身份升级全部废弃：更新登录夹具和设备鉴别，保留锁价、十进制、事务、幂等、预约竞争和状态断言。新增测试必须CTest可发现或在总验收命令中明确列出；零测试、跳过测试、缺GUI依赖不算通过。

## 7. 一人可操作的最终演示流程

由M1启动器一次启动服务，runbook列准确命令、账号获取方式及窗口入口；演示中只切窗口/点按钮，不需要临时改SQL或源码。若场景需要切换，用模拟器自己的控制界面或启动器场景命令面板；未实现面板则提前打开明确命名的控制终端，不能声称已有图形控制页。

**正常链（至少两轮）：**

1. 运营端记录站点费率、用户余额和今日营收；Web显示数据源与更新时间。
2. 车主登录，查看附近站点/详情，选择正常桩预约开始。
3. 模拟器正常上报，车主用量增加，运营端出现活动订单；Web正在充电数变化。
4. 车主停止，核对用量×锁价的两位小数金额；充值（必要时）并支付。
5. 展示历史订单、余额、运营营收、Web收入，逐项与数据库只读断言对照。
6. 第二轮新订单应从新的累计基准开始，不继承上一单电量；不必重置库。

**故障链（至少两轮，分别高温与离线）：**

1. 选择另一个可服务桩开始订单，触发场景。
2. 展示车主停止计量/待支付，运营告警和工单，Web对应变化。
3. 处理工单、恢复设备、结清订单、按规则解除禁用；恢复顺序符合合同。
4. 再次查询设备可服务性，验证没有自动复活旧充电单或多收电费。

双轮是同一候选版本的稳定性抽查，不要求反复重跑不变历史测试。修复后对失败项和影响范围回归；最后一次全量构建/测试通过后不得继续改代码却沿用旧证据。

## 8. 最终门槛、交付与恢复

必选功能缺失、扣款/计量错误、越权、数据损坏、静默Mock、三端不同库、关键流程无法运行都是阻断。任一A项或原需求必过项FAIL/BLOCKED，整组不能PASS。非阻断的小视觉问题可列限制，但不能把不可点击按钮当小视觉问题。

交付到 `docs/stage1-release/`：

- `baseline.md`：来源和候选SHA、环境和组件路径。
- `contract-delta.md`：新增动作/字段/迁移、旧客户端影响、样例与测试。
- `task-status.md`：M1/M2/M3任务和需求逐项状态。
- `test-results.md`：精确命令、退出码、测试总数/跳过数、日志路径；区分历史证据与本次结果。
- `acceptance.md`：A01～A31及原需求映射的实际结果、两轮操作证据。
- `runbook.md`：从干净候选到启动、演示、停止的准确步骤；本机和跨机器连接设置。
- `known-limitations.md`：教学手机号登录、明文受控网络、基线预测、模拟支付、不接真实硬件/支付平台等；不掩盖未完成必选项。
- `rollback.md`：旧环境保持位置，候选停止方式，迁移库与头像备份恢复步骤；不能用旧二进制直接打开已升级库。

日志、截图脱敏；不提交令牌、运行库、node_modules、构建缓存和所有临时图片。Git仅显式添加审核过的文件。

默认交付到本地候选分支。向用户报告“实现及验收状态、候选分支/SHA、是否推送/合并/部署”；只有另获授权才推送、提PR、合并main或替换演示环境。回滚部署需要兼容的代码+数据库+头像备份组合，不执行数据迁移降级或覆盖旧库来碰运气。
